# Apptainer, GPUs, and MPI across Ruth, Jean, and Blueback

Research date: 2026-09-21. Public documentation only; no cluster login or execution was performed. Scheduler mappings supplied by the user remain authoritative for this plan: **Ruth/PBS, Jean/Slurm, Blueback/Slurm**. The public hardware summary agrees. [HPCMP systems summary](https://centers.hpc.mil/systems/hardware.html)

User-supplied constraint: AI development tools are approved on both login and compute nodes for these targets. This note does not independently assess that approval.

**Recommended structure.** Maintain one shared development-tools recipe, with CPU, CUDA, and ROCm image variants, plus three small host-side site profiles. Share editor configuration and workflows across these images. Treat GPU runtime and MPI combinations as separately qualified targets; allow additional image variants when a site's supported libraries require them. This is an engineering recommendation, not a claim that three images already cover every application.

HPCMP documents Apptainer support across production allocated systems, permits externally built containers, and identifies reference MPI/GPU containers and run scripts under `$SAMPLES_HOME/Singularity/examples`. Begin with those local examples. Its public guide describes mostly Apptainer 1.3.x, with some 1.2 installations; current upstream documentation describes 1.5. Record the installed version and use matching documentation before adopting newer options. [HPCMP Apptainer guide](https://centers.hpc.mil/users/docs/general/ApptainerUserGuide.html), [upstream guide](https://apptainer.org/docs/user/latest/gpu.html)

**What is established about the targets.** These are candidate `linux/amd64` targets based on the listed Intel/AMD processor families; confirm `uname -m` on the actual login and compute nodes. HPCMP explicitly distinguishes instruction-set-compatible Intel/AMD images from separate Arm/Power images. [HPCMP container portability guidance](https://centers.hpc.mil/users/docs/general/ApptainerUserGuide.html)

No current driver, ROCm/CUDA, exact MPI, or PMI version for all three targets was verified in this research. Ruth and Jean's detailed user-guide URLs were not retrievable through the research browser. These are discovery requirements, not reasons to guess versions.

**GPU compatibility.** `--nv` and `--rocm` expose devices and bind selected host libraries; they do not eliminate driver, hardware, or runtime compatibility requirements. NVIDIA library discovery depends on Apptainer configuration and the host library cache. Include the development toolkit needed to compile inside the appropriate image, then verify what libraries actually load. Do not assume that successful device enumeration establishes a working application stack. [Apptainer 1.3 GPU guide](https://apptainer.org/docs/user/1.3/gpu.html)

Select CUDA from the actual host driver and GPU architecture support. NVIDIA documents backward compatibility and more limited minor-version compatibility; new features and PTX can impose stricter driver requirements. Do not select the newest toolkit merely because its container starts. [NVIDIA compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)

Select ROCm using AMD's hardware, kernel-driver, and user-space matrix. AMD identifies MI200-series targets as `gfx90a` and MI300-series as `gfx942`; therefore Ruth and Blueback require different GPU code targets even when they share a ROCm image. AMD also notes that telemetry tools such as AMD SMI can have tighter driver dependencies. [AMD compatibility matrix](https://rocm.docs.amd.com/en/docs-7.14.1/compatibility/compatibility-matrix.html), [driver/user-space guidance](https://rocm.docs.amd.com/projects/install-on-linux/en/latest/reference/user-kernel-space-compat-matrix.html)

**MPI is a site contract.** Apptainer distinguishes two useful models:

- **Hybrid:** the host launcher starts Apptainer, while MPI libraries inside the image run the application. The implementations and process-management mechanisms must be compatible.
- **Bind:** the host launcher starts Apptainer and host MPI libraries are mounted into it. The application must have been built against a compatible MPI ABI. Mounting Open MPI cannot repair an application built for an incompatible MPICH ABI.

Both require the relevant interconnect libraries/devices. Prefer the model demonstrated by each site's supplied examples. Keep the scheduler and MPI launch command on the host: conceptually, `site-launcher apptainer exec image.sif application`. [Apptainer MPI guide](https://apptainer.org/docs/user/1.3/mpi.html)

PMI/PMIx is a separate compatibility axis from the MPI API/ABI. Record the launcher's supported plugin and the MPI build's corresponding support. Slurm documents `srun --mpi=list`, a Cray-specific `cray_shasta` plugin, and PMIx security-domain compatibility concerns. Do not globally prescribe `--mpi=pmix` for both Slurm systems. [Slurm MPI guide](https://slurm.schedmd.com/mpi_guide.html)

For Cray, HPE's ABI guidance requires dynamic linking, compatible compiler/OS environments, and an MPICH-ABI-compatible build; `cray-mpich-abi` is a documented route, subject to installed availability. HPE identifies OFI/libfabric as its default network interface, and the only supported netmod on Slingshot-11; the `cxi` provider supplies that network path. GPU-aware Cray MPI adds vendor GTL libraries and requires `MPICH_GPU_SUPPORT_ENABLED=1` for device-buffer MPI operations. None of this is supplied merely by `--nv` or `--rocm`. [HPE Cray MPI documentation](https://cpe.ext.hpe.com/docs/latest/mpt/mpich9/intro_mpi.html)

A practical adapter may need MPI, PMI/PALS, libfabric/CXI or InfiniBand/UCX dependencies, runtime configuration, and launcher sockets. Discover the exact dependency set from the site's examples and loaded libraries. LUMI's official Cray-container guidance demonstrates curated bindings for MPI/libfabric and Slurm runtime paths; its training notes also show that needed bindings change with image generations. This is evidence for a versioned site adapter, not a list to copy unchanged onto HPCMP. [LUMI container jobs](https://docs.lumi-supercomputer.eu/runjobs/scheduled-jobs/container-jobs/), [LUMI container training](https://lumi-supercomputer.github.io/LUMI-training-materials/2day-20251020/205-Containers/)

**Preserve the image's operating environment.** Do not bind the host's entire `/usr`, `/lib`, or `/lib64` over the image, or replace container glibc as an ad hoc missing-library fix. Such mounts hide image content; broad replacement defeats control over its binaries and library combinations. Choose a compatible base and bind only the required integration paths. This recommendation follows Apptainer's mount behavior and its warning that host/container libc distance can cause GPU library errors. [Bind behavior](https://apptainer.org/docs/user/latest/bind_paths_and_mounts.html), [libc compatibility warning](https://apptainer.org/docs/user/1.3/gpu.html)

Likewise, do not blindly add `--cleanenv` to MPI launchers. It removes host environment propagation. The profile must deliberately retain or reintroduce the scheduler, MPI, fabric, and GPU-selection settings needed by its tested launch path, while excluding unrelated Python/compiler settings. [Apptainer environment rules](https://apptainer.org/docs/user/1.3/environment_and_metadata.html)

**Storage is a separate profile.** Bind verified home/project/work paths and resolved symlink targets. Archives are NFS-mounted according to the ARL and Navy guides, but are tape-backed services intended for staging. ARL explicitly prohibits staging in compute queues and requires batch transfers to use the transfer queue. Navy recommends the portable `archive` command and discourages using archived files directly. Therefore, keep archive staging host-side; expose archive paths only in a separately chosen, eligible staging session. [ARL archive guide](https://centers.hpc.mil/users/docs/arl/archiveGuide.html), [Navy archive guide](https://centers.hpc.mil/users/docs/navy/archiveGuide.html)

**Qualification sequence — proposed acceptance criteria, still unexecuted:**

1. **Inventory and serial:** record node class, CPU ISA, OS/glibc, Apptainer mode/version, loaded modules, allowed binds, compiler/MPI versions, launcher, driver/toolkit versions, and image digest. Verify editor/tools, identity, project writes, and intended mount paths. Compare login and allocated compute nodes separately.
2. **One-node GPU:** compare native and container device enumeration; compile/run a small CUDA or HIP kernel with a known answer. Check allocation visibility, device target, loaded libraries, and monitoring tools. Exercise each GPU node class independently.
3. **Two-node CPU MPI:** first establish a native baseline; then run container rank/hostname reporting, point-to-point exchange, all-reduce, and small latency/bandwidth tests. Require correct ranks spanning both hosts, correct results, and evidence of the intended fabric rather than unnoticed TCP fallback. Repeat with multiple ranks per node.
4. **GPU-aware MPI:** test device-buffer send/receive and all-reduce within a node and across two nodes; verify rank-to-GPU placement, GTL/runtime loading, and compare native/container performance. A successful CPU-buffer MPI test does not satisfy this gate.
5. **Release:** record the passing image/profile/module combination and its limits. Requalify affected stages after changes to image base, GPU runtime, MPI, Apptainer, or site drivers. Retain the previous working image for rollback.
