# 0.7.3-preview4: workspace prompt and SSH transfers on rootless RHEL

**Follow-up:** The affected RHEL system confirmed that `scp` works after this update. Its prompt still lacks the `ws:` label; a sanitized diagnostic identified one scalar, read-only command rather than a single function. See [0.7.3-preview5](0.7.3-preview5.md) for the next prompt correction.

The affected RHEL system confirmed that 0.7.3-preview3 removed the `PROMPT_COMMAND: readonly variable` error, but its interactive prompt still lacked the `ws:` label. A fresh-entry diagnostic reported the correct release, layout, user ID, and prompt function, with a missing workspace hook, another prompt template, and a read-only `PROMPT_COMMAND`. The user's SSH transfer also failed on `/etc/ssh/config.d/50-redhat.conf`: the host reported owner `0:0`, mode `644`, while the workspace reported owner `65534:65534`, mode `644`. Both shells resolved `ssh` and `scp` from `/usr/bin`.

The Bash startup now checks the hook again after personal and site settings load. When a read-only hook names one function, the workspace retains that function and restores its own prompt after it runs. It also checks for the exact `_ws_prompt` array element; `_ws_prompt_restore` alone no longer counts as an installed workspace hook. A packaged Linux PTY regression reproduced the missing label on the prior Bash configuration, then passed with the correction, including a directory change.

For SSH, the native launcher now creates private, temporary, user-owned copies of the readable system SSH client configuration and files reached through `Include`. It binds those files read-only at their original paths for that one workspace entry. The host files are not modified; the launcher does not scan SSH keys or server configuration. A rootless Apptainer fixture showed a root-owned host config as UID `65534` inside and the bound copy as the workspace UID. An offline OpenSSH check rejected an included config owned by `65534` and accepted the same content owned by the workspace UID.

From a native shell in the checkout:

```bash
git pull --ff-only && ./setup
ws enter
```

Start a fresh entry or managed tmux server; an existing server retains its old image and launcher. Inside the new workspace, check the `ws:` label and try a small approved `scp` transfer. The local fixtures do not include the site's exact startup files, SSH `Include` graph, authentication, or network path. If either symptom remains, run `python3 scripts/diagnose-workspace-entry.py` once from the native shell and share its short report. The diagnostic does not print prompt, config, or key contents.
